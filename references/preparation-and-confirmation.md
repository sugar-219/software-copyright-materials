# 环境、项目证据与内容确认

用于新制作，或名称、申请版本、源码范围有变化的重新制作。既有材料只读审查不补造本记录；局部修订仅为本次新输入记录确认，原件按原哈希与映射核验。

## 1. 先检查环境

用当前会话实际可执行的 Python 运行，不默认 PATH 中的 python 或 py 可用：

```text
<Python> -X utf8 -B <skill>/scripts/check_environment.py --out-dir <工作目录>/preparation
```

生成 environment.json/md，列出解释器、依赖模块、约定字体、模板和 Word COM 注册情况；不安装依赖、不启动 Word、不改全局设置。环境诊断和核心扫描仅依赖 Python 标准库；PDF摘要按已安装的 pypdf 能力读取。

`preflight_passed` 只代表这些预检项目通过。Word 注册不代表 COM 可正常自动化，仍须通过真实导出、分页和视觉检查。预检失败不妨碍整理可核实证据与草稿，但不能承诺完整交付已就绪。缺依赖按 requirements.txt 使用独立环境；缺 Word 或字体时说明具体阻碍，不改用其他排版后端冒充完成。

## 2. 列证据，再由 agent 理解业务

```text
<Python> -X utf8 -B <skill>/scripts/prepare_project.py --project <项目目录> --out-dir <工作目录>/preparation
```

生成 project-evidence.json/md，记录路径、可读取文件的哈希、行数及文档摘要索引，不自动选择文件：

- `documents`：项目文档候选，包括 Word/PDF 等；可处理文档附开头摘要、标题及读取状态，仍需进一步阅读正文。
- `configuration_evidence`：依赖、配置等环境线索，不直接作为自主源码纳入。
- `source_candidates`：可读文本候选，不限编程语言后缀；`selected=false` 不是已确定排除。
- `excluded`：未遍历的依赖/生成目录、链接、明显二进制及潜在敏感配置等，并给出理由。
- `needs_review`：超2MiB、编码或读取有问题的文件，保留路径供进一步核对。

扫描只是初筛，不证明完整源码已识别。自定义生成目录、配置形式的业务代码、第三方源码、非标准编码等仍由 agent 分类。大文档也可能进入 needs_review；不能因为未自动提取正文而忽略。清单不复制 .env、私钥正文，也不跟随链接；这不等于完整敏感信息扫描。

阅读实际入口、核心逻辑、必要文档和运行证据后，在同一工作目录写简短的业务理解草稿，说明软件用途和用户、已核实的功能与操作流程、支撑文件、无法核实的事项。按实际项目组织，不要求固定章节或扩写到固定篇幅。说明书要写清入口、操作和结果，避免复述框架清单、营销套话和每章相同的通用步骤。

将主要功能写入统一输入的 business，按[功能资料与草稿检查](business-analysis.md)生成业务理解和材料文字预览，不再独立维护两份相同事实。摘要索引不能替代阅读全文。

涉及业务口径不明确时集中展示建议，请用户确认缺失或冲突的关键事实。已有会话确认可以直接引用；不要为了完成多个阶段重复询问相同内容，也不要要求用户读懂 JSON。

源码清单由 agent 阅读后形成，完整覆盖本次申请软件的自主源码范围，按固定顺序填入 input.json 的 source_files，在 source_exclusions 中记录实际排除项及理由。不固定前端优先，不为达到60页补入无关源码。候选清单不是源码范围完整性的证明。业务判断依据可写入 input.json 的 fact_evidence；不要把行业资料当成实际已实现功能。

截图优先使用已可用且获授权的真实运行方式，Web 项目可使用现有浏览器自动化。缺少条件时向用户说明需要哪些页面的截图；用户明确暂不截图时，保留可见预留文字，并在待办中说明。已能自动截图时无需再要求用户选择工具，不因截图需要静默安装软件。不给不可用的固定工具设强依赖。

## 3. 将已有确认绑定到内容

input.json 是唯一生成底稿，业务理解及候选清单留在工作目录辅助审阅。正式生成前展示名称、版本、开发方式、业务口径、源码范围和排除理由，以及说明书/申请信息/必要协议的草稿或变化。按照当前任务和会话已有授权核对确认；不新增逐阶段强制暂停。已有确认或明确授权足够时不重复询问，否则等待缺失的关键确认。

在实际确认后保留 software.confirmed=true，并记录确认的具体内容或会话依据：

```text
<Python> -X utf8 -B <skill>/scripts/confirm_input.py record --project <项目目录> --data <工作目录>/input.json --note "<实际用户确认或已有授权依据>"
<Python> -X utf8 -B <skill>/scripts/confirm_input.py check --project <项目目录> --data <工作目录>/input.json
```

记录文件自动为输入文件同目录下的 `<输入文件名去扩展名>-confirmation.json`。生成器 build 和 revise 都会在写文件前校验；只有 confirmed=true 不再足够。

绑定三组内容：

- identity：软件字段（除 confirmed 布尔值）。
- source：源文件列表、顺序、编码、实际文件字节哈希、排除说明及排版策略。
- content：申请信息、说明书、合作协议、字段限制、事实依据及引用图片字节哈希；有 business 时同时绑定功能资料及其引用文件字节。

JSON 缩进和键顺序变化不会使记录失效；引用源码或截图内容、以上字段变化会使记录失效。规则检索日期、规则记录不属于用户事实确认指纹，仍须单独核验其适用性。新增但尚未列入 source_files 的文件不会自动加入范围，须重新检查范围完整性。

失效时先说明受影响部分，按已有授权判断是否足够；不足时只确认该变化，再更新记录。不能只改指纹或写虚构 note 来通过检查。记录仅证明所记录内容的对应关系，不证明真人操作、原创性、权属或登记通过。

生成器把实际使用的确认记录复制到单次运行目录的 input-confirmation.json。不要删除旧输入的记录来伪装从未发生变化，也不要把这份内部记录放入交付目录。

旧版本材料没有该记录仍可审查；不得改动原件来补造历史确认。使用 revise 时为新输入记录本次确认即可，旧基线仍按真实检查、哈希和映射判断可否复用，不因缺少本次新增记录重制未变源码。

## 4. 维护验证

```text
<Python> -X utf8 -B <skill>/scripts/test_materials.py --temp-root <独立测试目录>/materials
<Python> -X utf8 -B <skill>/scripts/test_preparation.py --temp-root <独立测试目录>/preparation
<Python> -X utf8 -B <skill>/scripts/test_business_review.py --temp-root <独立测试目录>/business
```

新增测试核对内容变化、源码/图片字节变化、目录边界、只读扫描、依赖诊断和旧基线局部复用。测试夹具与模拟记录不能用于任何实际项目的检查结论。
